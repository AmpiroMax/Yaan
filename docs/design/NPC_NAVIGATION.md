# Навигация НПС: контракт первого среза

## 1. Что есть (по коду) и чего нет

- Исполнитель `execute_npc_actions` (NpcAction.cpp) ведёт MoveTo ПО ПРЯМОЙ:
  рыск к цели `NPC_TURN_RATE`, ход в конусе `NPC_MOVE_CONE_DEG`, приход по
  `NPC_ARRIVE_RADIUS`, застревание `NPC_STUCK_S`/`NPC_STUCK_PROGRESS_M` →
  `PathBlocked`. Физику не спрашивает вовсе (`(void)physics`).
- Интерфейс физики (IPhysics.h) даёт только `raycast` и `sphere_cast`;
  перечислить построенную статику нельзя (ручки непрозрачны). Нулевой
  бэкенд — без коллизий: все тесты НПС идут без стен.
- Коллизию карты собирает приложение из четырёх источников (AppHouse.cpp,
  AppWorld.cpp): суп треугольников домов и мебели (`house_positions_`
  хранится, индексы — нет), меши деталей сцены по тайлам, ящики стволов и
  предметов, рельеф — воксельная поверхность чанка (высота на CPU —
  `ChunkManager::height_at`). Всё это есть на CPU ДО физики.
- Тела НПС: `NPC_BODIES_MAX` 3, тик без замера цены; патруль
  (Wait + MoveTo по точкам) живёт в приложении (NpcBodies.cpp before_step) —
  это поведение не в той зоне.
- Запертая капсула (§16.9): машина встаёт и стоит; сигнала исполнителю нет.

## 2. Сетка проходимости из геометрии (не из физики)

Постройка чисто из геометрии, чтобы шла в тестах без окна и без Jolt (образец —
SeatApproachTests: `read_scene` + `read_house` + `build_house_mesh`) и чтобы не
трогать IPhysics. Вход — plain data:

```
struct NavInput {            // engine/gameplay/sources/NavGrid.h
  std::span<const NavMesh> meshes;   // {positions, indices} — дома, детали, воксели
  std::span<const NavBox>  boxes;    // {center, half_extents, yaw} — стволы, предметы
  float (*ground)(void*, glm::vec2); void* ground_ctx;   // высота рельефа
  glm::vec2 min_xz, max_xz;          // охват (карта или стенд)
  NavAgent agent;                    // radius, height, step, max_slope — из NUMBERS
};
```

Постройка — столбцы по ячейкам `NAV_CELL_M` (0,25 = меньше радиуса капсулы
0,35): растеризация треугольников и ящиков в пролёты твёрдого по высоте
(квант `NAV_HEIGHT_Q_M` 0,05), сверху рельеф. ЭТАЖ = верх твёрдого пролёта с
просветом ≥ `PLAYER_CAPSULE_HEIGHT` над ним и наклоном ≤ `PLAYER_MAX_SLOPE`
(грань треугольника — по нормали). Один столбец может держать несколько
этажей (пол дома и его крыша, мост и земля под ним). Соседние этажи связаны,
если |Δh| ≤ `PLAYER_STEP_HEIGHT` (0,35: подступёнок марша 0,18 — проходим,
откос круче 49,8° — нет, потому что его грани не этажи). Эрозия на радиус:
этаж, у которого в круге `PLAYER_CAPSULE_RADIUS` есть столбец без этажа на
той же высоте (стена, обрыв), — непроходим; так путь держит 35 см от стен
без запросов к физике. Это подход Recast (heightfield → compact → erode) без
полигонизации: первый срез идёт A* прямо по этажам.

Порог эрозии — от центра ячейки: этаж с фаской d (половины ячейки) стоит
центром на (d/2 + 0,5)·ячейка от края столбца препятствия, съедается при
d < 2·(r/ячейка − 0,5); центр пути ≥ r от любой грани по построению, проход
в три свободные ячейки (0,75 м) открыт. Recast берёт ceil(r/ячейка) — на
0,25 при 0,35 это отодвигало путь на 0,75 м и закрывало проходы уже 1,75 м.
ХВОСТ: дверь 0,9 м проходима, только если в неё легли три целые ячейки;
сдвинутая на полъячейки — закрыта. Двери вне первого среза (§8), при их
подключении — ячейка 0,125 в кармане интерьера или дверь как явное ребро.

**Цена (условие 2 синка, замер `diagnostic_whiterun_build_cost`, без окна,
read_scene + read_house):** whiterun.scene — 868 домов, 2,19 млн треугольников
(полный меш, включая убранство; коллайдер — подмножество), охват 197 × 159 м,
500 532 столбца, 669 604 этажа (559 877 проходимых), 6,48 млн пролётов;
постройка 350–390 мс, результат 11 МБ, пик постройки 143 МБ (пролёты
16 байт × 6,5 млн). Ниже порогов ~1 с / ~200 МБ — первый срез строит одну
сетку на карту; тайлы 32 м по требованию — когда придёт мир атласа с бо́льшим
охватом (§8). Стенд interaction: 8 домов, 5 144 треугольника, 25 344 столбца,
25 601 этаж, 24 477 проходимых.

Постройка раз при загрузке карты, из тех же треугольников, что уходят в
физику (`house_positions_` + индексы, которые начнут храниться; тайловые меши
деталей; воксельная поверхность чанка через `voxel_mesh`; ящики) — ОДНИМ
сборщиком: `NavInput` — его выход, не вторая сборка (условие 1 синка).
Прибор в приложении: число треугольников и `nav_geometry_hash` у сетки и у
коллайдера совпадают на стендах interaction и stairs; контроль — дом,
добавленный только в одну из двух, красен (в `sim_nav_grid` заготовка: лишний
ящик меняет хэш и счёт).

## 3. Путь

- `nav_find_path(grid, from, to, out)` — A* по этажам, 8 соседей, стоимость —
  евклидова с диагональю √2, эвристика та же; отказ вслух, если старт или
  цель не на этаже (ближайший этаж в `NAV_SNAP_M` 0,5, иначе `PathBlocked`).
- Натяжение (string pulling): по цепочке ячеек — жадное удаление точек, пока
  отрезок между соседями проходим (проверка «линия по ячейкам» той же сетки,
  с той же эрозией). Путевые точки — углы; приход к точке по
  `NAV_WAYPOINT_M` 0,3, к последней — по радиусу MoveTo.
- Путь — plain data `NavPath{points, next}`; хранится в скрэтч-компоненте
  исполнителя (как `NpcMoveProgress`), не в действии.

## 4. Шов с исполнителем

- MoveTo: на активации — план; ход к `points[next]` тем же конусом и рыском,
  что сейчас (прямая — частный случай пути из одной точки). Нет сетки
  (`nav == nullptr`, старые тесты на нулевой физике) — прямая, как сейчас.
- ПЕРЕПЛАНИРОВАНИЕ: (а) машина заперта (§16.9) — сигнал `blocked` приходит в
  `StepContext::LocomotionRequest` (из `anim::LocomotionOut`); исполнитель
  помечает столбец перед НПС временно закрытым на `NAV_BLOCK_TTL_S` и
  планирует заново; (б) прежний застой `NPC_STUCK_S` остаётся второй линией;
  (в) больше `NAV_REPLAN_MAX` перепланов на одно MoveTo — `PathBlocked`.
- ОБХОД ИГРОКА И НПС (простой): персонажи — из ECS (Transform + капсулы), не
  из физики. Другой персонаж в `NAV_YIELD_M` (2·радиус + 0,3) впереди по ходу
  (конус ±45°) — стоп и ждать до `NAV_YIELD_S` (1,0); уступает тот, у кого
  больше `EntityId` (детерминированно, без взаимного ожидания: у пары
  уступает один); истёк срок — переплан с чужим столбцом закрытым кольцом в
  два радиуса капсулы на `NAV_BLOCK_TTL_S` (эрозия временных блоков не
  считается), и тот, кого обходим, встречным больше не считается — иначе
  стоящий игрок держал бы НПС вечно (первый прогон: 305 тиков уступания и
  тупик). Игрок никогда не уступает.
- ПОСЛЕ ПЕРЕПЛАНА ПО `blocked` — `NAV_REPLAN_GRACE_S` (1,0) сигнал не
  считается: защёлка машины держится, пока новый ввод не ушёл дальше
  `LOCO_BLOCKED_RELEASE_DEG`, и без паузы `NAV_REPLAN_MAX` выбирался бы за
  четыре тика, не за четыре тупика (замер: три запертых тика — три
  переплана). Стартовый план — не переплан. Столбец впереди закрывается
  кольцом 3×3, чтобы обход отклонил ввод дальше порога защёлки.
- СКРЭТЧ ПОИСКА живёт в `NavContext{grid, search}` у владельца карты (App,
  прибор), исполнитель получает указатель: не в сетке (const, общая), не в
  системе (правило 9), не в НПС (12 МБ на whiterun × тел). Отступление от
  буквы синка «`+ const NavGrid*`» — тот же смысл, названо.

## 5. Поведения поверх очереди (правило 15)

Компонент plain data `NpcBehaviour` (variant: `Wander{center, radius,
pause_s}`, `Patrol{points, loop}`, `Follow{target, distance}`,
`LookAtNearby{radius}`) и система `run_npc_behaviours(world, tick)`: ТОЛЬКО
`enqueue` существующих действий и ТОЛЬКО когда очередь пуста (LookAtNearby —
`Face` при пустой очереди и игроке в радиусе; уйдёт — поведение молчит).
Wander: случайная цель на этаже в радиусе (ГСЧ splitmix64 в gameplay, зерно =
зерно карты ⊕ EntityId ⊕ тик — прогон записи совпадает), потом `Wait`.
Follow: `MoveTo` к точке «цель минус distance по её курсу», переочередь, когда
цель ушла дальше `distance + NAV_FOLLOW_SLACK_M`. Патруль из NpcBodies.cpp
переезжает сюда как `Patrol` (приложение больше не заказывает действия).

## 6. Число тел и цена тика

`NPC_BODIES_MAX` 3 — это НЕ бюджет, а полоса номеров мешей: 192 + k·18 в
128..255 (ProcMesh.h) вмещает ровно три тела (четвёртое — 246 + 18 > 255).
Выход не в расширении полосы: `SkinnedDraw` несёт палитру НА КАЖДЫЙ РИСУНОК
(IRenderer.h: «a palette is per-draw by construction»), то есть все НПС
одного тела могут рисоваться ОДНИМ зарегистрированным мешем — регистрация
раз на АССЕТ (условие 3 синка: ключ — хэш выпечки: .dfo тела с пресетом,
наборы частей и одежды; НЕ имя HumanBase, иначе первый НПС другого пресета
или народа молча получил бы чужое тело); `NPC_BODIES_MAX` становится
бюджетом тика, 16 в первом срезе, громкий отказ сверх него остаётся. Замер
мс на НПС по частям:
скиннинг (`build_draw`), стопы, машина+advance, навигация (план и слежение),
в HUD и CSV телеметрии; сверх бюджета `NPC_TICK_BUDGET_MS` — отказ вслух при
спавне. Редкий тик дальних (`NPC_FAR_M`): скиннинг и стопы через кадр —
делается, если замер показывает, что скиннинг — половина цены; иначе не в этом
срезе.

## 7. Что меняется (синк по правилу 26), числа, приборы

Публичные контракты:
1. НОВОЕ `engine/gameplay/sources/NavGrid.{h,cpp}`: `NavInput`, `NavGrid`,
   `nav_build`, `nav_find_path`, `nav_line_walkable`, `NavPath`. Чистые
   функции и plain data (правило 8/9). Зона sim (gameplay), без физики.
2. ИЗМЕНЕНИЕ `execute_npc_actions(world, physics, events, sim_tick)` →
   `+ const NavGrid* nav` (nullptr — прямая, как сейчас).
3. ИЗМЕНЕНИЕ `StepContext::LocomotionRequest` + `bool blocked` (капсула
   заперта, §16.9) и `anim::LocomotionOut` + `bool blocked`.
4. НОВОЕ `NpcBehaviour` (компонент), `run_npc_behaviours` (система) в
   `engine/gameplay/sources/NpcBehaviour.{h,cpp}`; поле `patrol` из
   `NpcBody` (app) уходит.
5. Приложение: `NavInput` собирается там, где собирается коллизия (AppHouse:
   хранить индексы домов; AppWorld: тайловые меши и ящики; рельеф через
   `height_at`), `nav_build` после загрузки карты; DFN_DRAW_NAV — отладочная
   отрисовка этажей (через существующий путь DFN_DRAW_COLLIDERS).
6. IPhysics — НЕ ТРОГАЕТСЯ. Набор NpcAction — НЕ РАСШИРЯЕТСЯ.

Числа (кандидаты в NUMBERS.md): `NAV_CELL_M` 0,25; `NAV_HEIGHT_Q_M` 0,05;
`NAV_SNAP_M` 0,5; `NAV_WAYPOINT_M` 0,3; `NAV_BLOCK_TTL_S` 3; `NAV_REPLAN_MAX`
4; `NAV_YIELD_M` 1,0; `NAV_YIELD_S` 1,0; `NAV_FOLLOW_SLACK_M` 1,0;
`NPC_BODIES_MAX` 16; `NPC_TICK_BUDGET_MS` (по замеру); `NPC_FAR_M` 30.
Агент берёт `PLAYER_CAPSULE_RADIUS/HEIGHT`, `PLAYER_STEP_HEIGHT`,
`PLAYER_MAX_SLOPE` по именам.

Приборы (каждый с контрольной рукой; стенды interaction и stairs, Jolt из
тех же треугольников, что и сетка):
- `sim_nav_grid`: этажи на плоскости, столбец под столом — этаж пола и этаж
  столешницы, эрозия 0,35 у стены, марш 0,18/0,28 связан, откос 54° — нет,
  33° — да (мосты стенда stairs); контроль — агент с шагом 0,1 марш не берёт.
- `sim_nav_path`: путь вокруг стола короче обхода по периметру и длиннее
  прямой; натяжение убирает точки; контроль — без эрозии путь режет угол.
- `app_npc_nav` (Jolt): interaction — к цели за столом без касаний капсулы
  (`character_contacts` пуст, кроме пола); stairs — с площадки на террасу по
  маршу, дошёл; стена поперёк — заперто → переплан → дошёл (контроль:
  `nav == nullptr` — `PathBlocked`); 8 НПС Wander минуту: доля доездов,
  застреваний > 2 с — ноль, расстояние между капсулами ≥ 2·радиус, длина
  пути / оптимум ≤ 1,3, снос стоп по LocoTelemetry как у игрока, мс на НПС.
- Кадры и лента — `artifacts/reports/npc-navigation/`.

## 8. Вне первого среза (условие 4 синка, названо)

- ДВЕРИ И ИНТЕРЬЕРЫ: карман интерьера (Y −1000) и порталы — путь сквозь
  дверь как ребро между двумя сетками (улица ↔ карман); ячейка 0,125 в
  кармане или дверь как явное ребро (см. хвост о ширине двери в §2).
- ПОДВИЖНАЯ УТВАРЬ `LAYER_LOOSE` в сетку не входит: упёрся — `blocked`
  (§16.9) и временное закрытие столбца на `NAV_BLOCK_TTL_S`, как у стены.
- ДАЛЬНИЙ РЕДКИЙ ТИК (`NPC_FAR_M`) — только по замеру мс на НПС (§6).
- СЕТКА ТАЙЛАМИ 32 м по требованию вокруг НПС, выгрузка с тайлом — когда
  охват карты превысит порог (§2: whiterun ниже порога).
- НАВИГАЦИЯ ПО РЕЛЬЕФУ МИРА (воксельная поверхность вместо `height_at`:
  тоннель в скале, нависания) — при подключении к карте мира.

## 9. Состояние

- `NavGrid.{h,cpp}` + `sim_nav_grid` (7 случаев) + `sim_nav_path` (5 случаев)
  сданы первым куском вместе с этой запиской; числа §2 — с этого прогона.
- Шов исполнителя сдан вторым куском: `execute_npc_actions(…, NavContext*)`,
  MoveTo по путевым точкам, переплан по `blocked` (LocomotionOut →
  LocomotionRequest → WalkerLocomotion прошлого тика), по застою и по
  истёкшему уступанию, `npc_nav_report` для приборов; `sim_npc_actions` +3
  случая (стена: 7,29 м обхода против 5,49 прямой сквозь стену в контроле;
  три запертых тика — один переплан, заперто навсегда — PathBlocked на пятом;
  уступает больший id, игроку — всегда, обход за один переплан). Без
  контекста — прямая, старые случаи целы.
- Поведения сданы третьим куском: `NpcBehaviour.{h,cpp}` (Wander / Patrol /
  Follow / LookAtNearby, только enqueue при пустой очереди; ГСЧ splitmix64
  без состояния от зерна ⊕ id ⊕ тик), патруль стендового бота уехал из
  NpcBodies в компонент `Patrol`, приложение зовёт `run_npc_behaviours` до
  исполнителя (сетки у приложения пока нет — nullptr). Уроки: Face при
  пустой очереди ставился бы каждый тик — порог `NPC_LOOK_REFACE_DEG`;
  Follow перезаказывает по `NAV_FOLLOW_SLACK_M`, а не каждый шаг цели.
  `sim_npc_behaviours` 6 случаев (система не трогает Transform; брожение
  детерминировано, в радиусе, по сетке мимо стены — контроль без сетки 364
  тика в стене; патруль по кругу и до конца; следование держит 2,5 м шагом
  и перезаказывает 23 раза за 4 с бега ведущего; взгляд — один Face, не
  шторм, капсулу игрока двигает teleport_character).
